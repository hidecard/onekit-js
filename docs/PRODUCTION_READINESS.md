# OneKit JS V3 Production Readiness

## Executive position

OneKit JS V3 is a usable compact browser framework and a credible foundation for small-to-medium applications. It is **not yet feature-equivalent to React plus Next.js**, because those ecosystems include a mature renderer, routing conventions, server components or server data APIs, error and loading boundaries, an extensive package ecosystem, mature DevTools, and years of compatibility testing. OneKit can become production-usable without copying every React or Next.js feature, but it must first establish stable contracts around rendering, reactivity, routing, SSR, tooling, and releases.

> Production-ready means that the framework has explicit contracts, predictable failure behavior, repeatable builds, tested upgrade paths, and documented limits—not merely that a demo renders.

## Highest-priority work before production adoption

### 1. Freeze the public contract

Every exported API needs a documented signature, return value, lifecycle rule, error behavior, and stability label. The project should distinguish stable APIs from experimental APIs such as streaming SSR, hydration, web components, and advanced plugin behavior. A compatibility test should import the package through the root entry point and every advertised subpath in both ESM and CommonJS contexts.

### 2. Harden reactivity

The reactive engine needs deterministic effect cleanup, a documented scheduler, stoppable watchers, cleanup callbacks, deep traversal rules, array mutation coverage, and protection against stale dependencies. The current V3 work adds proxy identity caching, dependency cleanup for reruns, an explicit `stop` helper, array length/index invalidation, and deep-watch coverage for array additions and nested mutations. Cleanup callbacks and additional scheduler guarantees remain follow-up work; the core scheduling behavior is already covered by the current regression suite.

### 3. Replace the minimal router with an application router

The V3 router now supports exact and dynamic paths, query strings, params, nested route composition, browser history, hash and memory modes, navigation guards, async loaders, cancellation, scroll behavior, prefetch, lazy components, route-level metadata composition, query-client integration, a `createRouter` factory, and the optional `createRouterView()` VDOM binding. The helper renders only committed matches and leaves the route-to-view function under application control. The remaining framework-level work is broader browser compatibility coverage, adapter-level streamed route manifests, and application-specific cache policy. It is not a drop-in replacement for Next.js routing.

### 4. Establish SSR and hydration parity

**M4 baseline status:** SSR now preserves request-scoped context through nested elements and components, escapes text and attributes, safely renders metadata, and remains import-safe in Node. Hydration reports structural mismatches and returns a disposer for listeners without silently rewriting server DOM. Error and loading boundary primitives are available for render, loader, and SSR adapters.

Remaining SSR work includes a complete application transport around the trusted route-data snapshot, sensitive-data and serialization policy, advanced async concurrency, stronger queue/back-pressure cancellation semantics, and a larger browser compatibility matrix. Adapter-level scheduling is available as an optional hook and covered by regression tests; progressive fallback/content boundaries, client continuation, and one-shot matching route-data reuse are also covered, alongside deterministic Promise scheduling, original render failures, and AbortSignal cancellation.

### 5. Improve component rendering architecture

The current options-style component API is useful, and the renderer now documents a consistent first update model: VDOM reconciliation for element children, keyed function components, and keyed stateful component instances, with template patching remaining a separate path. Keyed list moves, keyed function-component prop updates, state preservation across keyed moves, stable component root identity, lifecycle continuity, callback/object refs, ref cleanup, event listener cleanup, named VNode/default slot normalization, stateful hydration binding, component metadata synchronization, error boundaries, and unmount cleanup have baseline coverage. The opt-in Vite component-boundary validator now rejects client-to-server static imports, but it does not provide a Server Components runtime or transport. Remaining parity work includes hydration behavior for component-owned effects and advanced slot scheduling/async policies.

### 6. Make the CLI a complete project workflow

The CLI should provide `create`, `dev`, `build`, `preview`, and `test` commands with consistent exit codes and helpful diagnostics. Core failures now include stable error codes and hints for unknown commands, invalid options, invalid projects, and child-process startup failures. The starter should include TypeScript configuration, an application entrypoint, a production build, a test example, and a clear SSR option. The optional full-stack starter additionally generates `server.mjs`, `dev:server`, `start`, `.env.example`, graceful shutdown, and `/api/health`. CLI acceptance tests should run on Linux, macOS, and Windows path conventions where possible. The current suite covers inline option syntax, absolute output paths, and full-stack generation in addition to POSIX-style cwd and exit-code checks.

### 7. Establish the backend application layer

OneKit now has an adapter-neutral backend foundation plus an official lightweight Node HTTP bridge. Typed `ServerError`/`createServerError()` responses provide safe public application failures with status, codes, details, headers, and default production redaction; a resilient `errorResponse` hook supports application-owned envelopes without allowing failing telemetry hooks to crash the request. `createServerData()` now provides a small server-safe data boundary with request/abort context, concurrent-load deduplication, optional TTL caching, invalidation, and an injectable cache contract. The beginner path is `createApi()` with concise `context.ok()`, `context.json()`, `context.text()`, `context.fail()`, and one-read typed `context.body<T>()` helpers. `app.resource()` registers common collection/ID CRUD routes with one readable declaration. The lower-level `createServerApp()` API supports ordered middleware, decoded route params, query values, JSON validation, request state, the existing dependency injector, and an optional typed `context.database` adapter. `createNodeHandler()` connects the app to Node HTTP, while `app.handle(request)` remains suitable for serverless and edge adapters. Authentication/authorization contracts, `securityMiddleware.session()`/`token()` provider adapters, bounded in-memory rate limiting, configurable CORS preflight handling, and graceful lifecycle hooks are available. Rate limiting also accepts a portable `RateLimitStore` contract and `createMemoryRateLimitStore()` helper, so Redis, database, or edge-backed counters can be injected without changing route code. Node deployments can use the optional driver-injected `createRedisRateLimitStore()`; its atomic EVAL script maps an ioredis-compatible client to distributed increment/expiry behavior without bundling a Redis dependency. Database drivers, credential verification, identity/session storage, distributed store implementations, and server-only secret handling remain application responsibilities. The CLI also supports an optional `onekit create <name> --full-stack` starter that generates a minimal Node API entrypoint, health route, graceful shutdown, environment template, and server scripts. The server-data layer intentionally does not include an ORM, credentials, or a vendor-specific Redis driver; applications inject their own distributed cache implementation and keep server resources request-isolated. Larger applications can now use decorator-free `defineModule()`, `defineController()`, and `app.module()` composition with nested imports, providers, middleware, controller prefixes, and grouped routes. This is an organizational layer over the existing injector and router, not a promise of NestJS-compatible decorator metadata. Node applications can also use the optional driver-injected `createSQLiteAdapter()` for better-sqlite3-compatible handles, `createPostgreSQLAdapter()` for pg-compatible pools, and `createMySQLAdapter()` for mysql2-compatible pools; the core package does not bundle native database dependencies, and applications retain ownership of credentials, migrations, schemas, retries, and pool configuration. MongoDB is available through the document-native `createMongoDBAdapter()` collection boundary rather than the relational `DatabaseAdapter` contract. MongoDB transactions, indexes, aggregation, and schema validation remain application-owned.

### 8. Add production observability and failure boundaries

Applications need framework-level error capture for render errors, effect errors, event handler errors, router loader failures, and SSR failures. OneKit now exposes `createErrorReport`, `setErrorReporter`, and `errorHandler`; reporters receive a normalized `{ context, error: { name, message, stack? } }` payload, are opt-in, and are isolated so reporter failures cannot break application execution. When DevTools is enabled, failures also produce a `runtime:error` diagnostic event containing the normalized payload. The `onekit-error` DOM event remains available for browser integrations, while applications should avoid forwarding reports to external services unless they have reviewed and redacted their own messages and stacks.

### 9. Release safely

Before publishing a new release, the package should pass type-checking, all tests, production build, package dry-run, subpath import checks, and a clean-install smoke test from the generated tarball. For 3.1.19, these release checks pass: 35 Jest suites and **195 tests**, declaration verification, API export-map ESM/CJS verification, clean package installation, published registry verification, and `onekit-js-3.1.19.tgz` generation. A changelog entry, migration notes, and a versioned API stability matrix accompany the release. The SSR scheduling hook and richer ref semantics are additive and backward compatible, while vendor database/Redis drivers remain optional application dependencies. The Git tag, GitHub Release, npm publication, and post-publish registry verification are complete.

The public API stability policy and automated ESM/CJS export-map contract are documented in [`API_STABILITY.md`](./API_STABILITY.md).

## What OneKit should not promise yet

OneKit should not currently claim to be a drop-in React replacement, a Next.js replacement, or a complete NestJS/Express server platform. It should describe itself as a **compact TypeScript-first full-stack framework foundation with components, templates, JSX, stores, routing, SSR utilities, a beginner-friendly backend API, and a practical CLI**. That positioning is accurate and gives the project room to grow without creating compatibility expectations it cannot yet satisfy.

## Adoption recommendation

Teams can use the current release for documentation sites, interactive pages, internal tools, prototypes, and small browser-first applications after pinning the exact version and keeping an escape hatch to standard DOM APIs. For high-risk production applications, wait until async/streaming SSR semantics, the complete CLI workflow, renderer benchmarks, and clean-install release checks are complete.
