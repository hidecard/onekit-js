# OneKit JS V3.2.0 Roadmap

**Status:** Release candidate preparation

**Baseline:** `onekit-js@3.2.0` candidate, `create-onekit@1.0.10` candidate, branch `V3`

**Planning principle:** V3.2.0 should improve application-level production capability without destabilizing the V3 renderer, public exports, or existing SSR and hydration contracts.

## 1. Release objective

OneKit JS V3.2.0 will move the project from a hardened renderer and backend foundation toward a dependable application runtime. The current implementation increment makes route-driven applications easier to build through an explicit SSR route-data envelope, shared cache tags/revalidation, an opt-in file-route Vite plugin, stronger static Server/Client boundary checks, and a required cross-browser CI matrix. It improves developer experience without bundling a mandatory ORM, authentication provider, deployment platform, or vendor-specific runtime into the core package.

> **V3.2.0 theme:** predictable route data, explicit application boundaries, and a smaller gap between a working prototype and a production application.

## 2. V3.1.19 baseline

V3.1.19 already provides stateful hydration binding, richer named slots, keyed reconciliation, typed route and loader primitives, SSR and streaming boundaries, query invalidation and hydration, full-stack server APIs, optional database and Redis adapter contracts, API export verification, four-browser Playwright coverage, versioned performance budgets, and Chromium lifecycle heap regression checks. The current branch additionally contains the reviewed V3.2.0 route-data/cache/plugin/boundary increment described below.

The published release validation includes **35 Jest suites / 195 tests**, 22 ESM/CJS runtime export checks, four-browser Playwright tests, slot-heavy update and reorder budgets, and a Chromium CDP lifecycle heap test. The current branch adds focused transport/cache/plugin/boundary regression coverage; the exact final count is established by the release validation run rather than copied into this planning baseline.

## 3. Scope pillars

| Pillar | Outcome | Priority |
|---|---|---:|
| Route data contract | An additive, explicit route/query handoff with request cancellation, bounded JSON-safe transport, hydration reuse, tagged invalidation, and retry compatibility | P0 |
| Route UX conventions | Consistent `loading`, `error`, `notFound`, `redirect`, and unauthorized behavior at route boundaries | P0 |
| Typed navigation | Generated or inferable route params, query types, loader data, and safe link helpers | P0 |
| SSR payload and cache safety | Request isolation, JSON-safe transport, payload versioning, cache policy, and client reuse without duplicate fetches | P0 |
| File-based application structure | Opt-in Vite file-route discovery with deterministic manifests, conflict diagnostics, route metadata, and explicit layout/middleware associations | P1 |
| Rendering modes | Explicit CSR, SSR, prerender/SSG, and hybrid route configuration | P1 |
| Developer tooling | Hydration diagnostics, route/data inspector, component tree, profiler marks, and actionable runtime errors | P1 |
| Integrations and migration | Official examples for auth, forms, databases, testing, observability, and React/Vue interoperability boundaries | P2 |

## 4. Proposed API direction

The API should remain adapter-neutral and avoid forcing a single state-management or database solution. The following shape is a direction for design discussion, not a final stable API commitment.

```ts
const route = defineRoute('/users/:id', {
  async load({ params, request, signal, context }) {
    return context.api.users.get(params.id, { request, signal })
  },
  loading: UserLoading,
  error: UserError,
  notFound: UserNotFound,
})

const result = useData(route, {
  cache: 'request-and-client',
  revalidate: 30,
})
```

The contract must define the lifecycle of `idle`, `pending`, `success`, `error`, `cancelled`, and `stale` states; the ownership of abort signals; the rules for server payload serialization; the behavior of retries and invalidation; and the boundary between framework cache policy and application cache storage.

## 5. Milestones

### M0 — Contract and compatibility freeze

M0 will document the V3.2.0 design RFCs, classify new APIs as experimental until acceptance criteria are met, add compatibility tests for all V3.1.19 exports, and define deprecation and migration rules. No existing Stable API may be removed or silently change semantics in this milestone.

**Exit criteria:** API RFCs are reviewed; ESM/CJS export checks remain green; the V3.1.19 test and browser budgets remain unchanged; and a migration note exists for every changed behavior.

### M1 — Route data lifecycle

M1 implements the first additive route data lifecycle increment around request-scoped context, cancellation, deduplication, hydration reuse, cache invalidation, retry policy, and explicit loading/error states. The secure envelope composes with existing `Router` and `QueryClient` contracts instead of creating a second incompatible cache system.

**Exit criteria:** server and client loaders share a documented result contract; aborted navigation cannot commit stale data; SSR payload reuse prevents duplicate initial fetches; request state is isolated between concurrent requests; and unit, SSR, hydration, and race-condition tests cover the lifecycle.

### M2 — Route UX and typed navigation

M2 will add route-level loading, error, not-found, redirect, and unauthorized conventions. Typed route helpers will cover params, query values, loader data, and link generation while preserving runtime validation for untrusted URL input.

**Exit criteria:** every route state has a deterministic rendering path; redirects and errors do not leak request data; generated/inferred types fail invalid route usage at compile time; and browser tests cover back/forward navigation, interrupted loaders, nested layouts, and hydration transitions.

### M3 — File-based routes and rendering modes

M3 now has an opt-in Vite foundation that compiles discovered pages to ordinary `Route[]` values and emits deterministic route, layout, middleware, and association metadata. It supports conflict diagnostics and configurable extensions without silently composing runtime layouts or middleware. Prerender/SSG output, explicit CSR/SSR/hybrid configuration, generated fully typed declarations, and runtime composition remain future increments. Runtime filesystem access is not required in the browser bundle.

**Exit criteria:** a generated TypeScript project can create nested routes from `src/routes`; production build output contains a deterministic route manifest; prerendered routes work without a server; and SSR, CSR, and hybrid routes can coexist in one application.

### M4 — Developer experience and observability

M4 will provide an opt-in OneKit DevTools bridge and a stable diagnostics format for component tree inspection, route transitions, data cache state, hydration mismatches, and performance marks. Production builds must not include development-only inspector payloads unless explicitly enabled.

**Exit criteria:** diagnostics are SSR-safe and redaction-aware; inspector lifecycle cleanup leaves no listeners or retained roots; browser performance budgets remain within V3.1.19 thresholds; and a minimal browser-based debugging guide is available.

### M5 — Ecosystem and release readiness

M5 will add official starter recipes and integration tests for forms/actions, authentication providers, database adapters, observability, deployment adapters, and testing. It will also establish V3.2.0 release notes, migration guide, package provenance, clean-install checks, and a compatibility report.

**Exit criteria:** starter examples pass install/type-check/test/build; adapter examples remain optional; package export and license checks pass; documentation examples are executable or explicitly marked conceptual; and the complete release checklist is green.

## 6. Non-goals for V3.2.0

V3.2.0 will not promise React Server Components parity, a proprietary ORM, built-in identity storage, a mandatory deployment platform, a universal cross-browser heap profiler, or a large meta-framework rewrite. It will not silently change the V3 renderer or turn application-owned route rendering into an implicit framework behavior.

## 7. Quality and compatibility gates

| Gate | Required result |
|---|---|
| Public API | Existing V3.1.19 Stable exports remain compatible; `npm run verify:api-contract` passes. |
| Unit and integration tests | Existing 195-test Jest baseline remains green; new route/data tests include cancellation and request-isolation cases. |
| Browser matrix | Chromium, Firefox, WebKit, and Edge retain hydration, slot-heavy update/reorder, controlled-input, keyed-list, and DOM-heavy coverage. |
| Performance | Existing hard budgets remain unchanged unless a documented benchmark review approves a versioned adjustment. |
| Memory | Chromium lifecycle heap growth remains below the configured hard budget; history comparison produces no unreviewed regression warning. |
| Packaging | Type-check, production build, declarations, package verification, clean install, ESM/CJS exports, and CLI smoke checks pass. |
| Documentation | README, API stability, V3 usage, framework guide, production readiness, performance benchmarks, migration guide, changelog, and release notes agree on version and capabilities. |
| Security | SSR payloads, route manifests, query state, and error details are treated as untrusted transport data; server-only modules do not enter client bundles. |

## 8. Recommended implementation order

The recommended order is M0, M1, M2, M3, M4, and M5. M1 and M2 should be completed before large ecosystem work because integrations built on an unstable loader or route error contract would create migration debt. M3 should preserve the existing `createFileRoutes()` behavior and compile conventions to ordinary route objects. M4 should remain opt-in until diagnostics payloads, redaction, and cleanup behavior are proven in CI.

## 9. Open decisions

Before marking V3.2.0 APIs Stable, the project must decide how server cache ownership and conflict resolution work across deployments, whether loader results may be streamed incrementally, how route authorization differs from route data loading, how replay protection and key rotation are supplied to route-data transport, which deployment adapters are officially supported, and whether DevTools is maintained in the main repository or a companion package. The file-route generation decision is currently an opt-in Vite plugin; it should not become implicit until generated typing and runtime composition are accepted.
